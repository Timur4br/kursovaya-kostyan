# Курсовая Костян

Система поиска предметов по данным камер. Пользователь задаёт вопрос о предмете, а система должна находить связанные обнаружения, место, время и видеофрагменты. Отдельные компоненты будут обрабатывать видео, обнаруживать объекты, строить траектории и формировать ответы.

Этот PR создаёт основу: **Docker Compose, PostgreSQL 17 с pgvector, SQL-миграции и минимальный Go-сервис `api_gateway`**. CRUD будет реализован следующим PR после проверки структуры БД. Фронтенда, распознавания видео, LLM и авторизации на этом этапе нет.

## Быстрый запуск

Нужен Docker Desktop с запущенным **Linux Engine** и Docker Compose v2. Устанавливать Go или PostgreSQL на компьютер для запуска через Docker не требуется.

1. Скопировать `.env.sample` в `.env` в корне проекта.
2. Заполнить четыре значения:

   | Переменная | Назначение |
   |---|---|
   | `POSTGRES_DB` | Имя базы, например `coursework` |
   | `POSTGRES_USER` | Имя пользователя БД, например `coursework` |
   | `POSTGRES_PASSWORD` | Свой непустой пароль |
   | `API_PORT` | Свободный порт на компьютере, например `18080` |

3. Из корня выполнить:

   ```sh
   docker compose up --build -d --wait --wait-timeout 120
   ```

4. Открыть `http://127.0.0.1:18080/readyz` (заменить порт, если выбран другой). Успешный ответ:

   ```json
   {"service":"api_gateway","status":"ready"}
   ```

`docker compose ps -a` покажет `db` и `api_gateway` в состоянии healthy, а `migrate` — завершившимся с кодом 0. Это штатно: миграции — одноразовая задача. На корневом адресе `/` будет 404: пользовательский интерфейс ещё не добавлен.

## Как запускаются сервисы

```text
db становится healthy → migrate применяет SQL → api_gateway проверяет БД и стартует
```

- `db`: образ проекта pgvector `pgvector/pgvector:0.8.7-pg17`, данные в Docker volume `postgres_data`.
- `migrate`: тот же Go-образ, команда `gateway migrate`, миграции Goose с блокировкой от одновременного запуска.
- `api_gateway`: HTTP-сервер на Go 1.27.4, драйвер pgx, порт доступен на хосте только через `127.0.0.1`.
- `tests`: дополнительный профиль Compose для тестов; при обычном запуске не поднимается.

База не публикует свой порт на хосте. Внутри Compose Go обращается к ней по адресу `db:5432`.

## Проверки

На Windows дважды нажать **`Verify.cmd`**. На Linux/macOS из корня выполнить:

```sh
sh scripts/verify.sh
```

Проверка собирает и запускает стек, проверяет миграции и ограничения БД, повторное применение миграций, затем записывает тестовую строку, перезапускает контейнер БД и проверяет сохранение строки. Тестовая строка удаляется после успешной проверки. Данные volume не удаляются. На Windows журнал сохраняется в `.local/verify.log`.

Для запуска только тестов с PostgreSQL:

```sh
docker compose --profile test run --build --rm tests
```

При установленном Go:

```sh
go test ./...
go vet ./...
go build ./services/api_gateway/cmd/gateway
```

Обычный `go test` запускает модульные тесты. Тесты PostgreSQL пропускаются, пока не задан `RUN_DB_TESTS=1` и параметры `DB_*`; профиль `tests` задаёт их автоматически. Интеграционные тесты создают отдельные временные схемы и удаляют их после завершения. Проверки сохранения volume вызываются отдельно скриптами `verify`.

GitHub Actions выполняет модульные тесты, форматирование, `go vet`, сборку и полный сценарий Docker Compose на временной CI-базе.

## Полезные команды

```sh
docker compose logs -f api_gateway
docker compose logs migrate
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker compose run --rm migrate
docker compose down
```

`down` сохраняет volume с данными. Для обновления Go-кода или миграций повторить команду запуска с `--build`. Перед обновлением базы с ценными данными нужна резервная копия. Изменение пароля в `.env` само по себе не меняет пароль в уже инициализированном PostgreSQL.

## Структура

```text
docker-compose.yaml                  Сервисы, зависимости и volume
.env.sample                          Имена настроек без значений
scripts/init-db.sql                  Первичная установка расширения vector
scripts/verify.cmd, verify.sh         Проверка стека и сохранения данных
migrations/                          Версионируемая SQL-схема, встроенная в Go-бинарник
services/api_gateway/
  Dockerfile                         Сборка, тестовый и runtime-образы
  cmd/gateway/                       Команды serve, migrate, healthcheck
  internal/config/                   Проверка настроек окружения
  internal/database/                 Подключение, миграции и интеграционные тесты
  internal/httpapi/                  Проверки работоспособности HTTP
docs/schema.md                       Сущности, связи и решения по ER-модели
.github/workflows/checks.yaml         Автоматические проверки PR
```

## Конфигурация и границы этапа

`.env` читается Docker Compose и не попадает ни в Git, ни в контекст сборки. Go получает настройки через окружение: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSLMODE`, `HTTP_ADDR`. Строка подключения собирается с экранированием пароля. Сам пароль и строка подключения не выводятся в журнал.

Это конфигурация разработки: пользователь PostgreSQL создаётся владельцем базы и может применять миграции, а внутри Docker-сети используется `DB_SSLMODE=disable`. Разделение ролей миграций и приложения, авторизация и внешнее размещение — отдельные задачи перед эксплуатацией.

pgvector установлен и проверяется запросом расстояния между векторами. Колонки embeddings и векторные индексы не создаются, пока не выбрана модель и размер её выхода. Параметры состояний сущностей и SQL-представление ER-модели описаны в `docs/schema.md` и подлежат проверке в этом PR.
